# MVP 范围、v1.0.0 定义与排程

## 建议的首发产品

将 v1.0.0 定位为：**macOS 优先、单用户、本地控制面、能明确审批和核对执行结果的 AI 任务助手。** 首发只声明实际通过安装、运行和升级资格的 macOS 版本与 CPU 架构。优先 Apple Silicon；Intel、Rosetta、Windows、Linux 分开列状态。

这是本方案建议的发行范围，不会自动改变原 M3 的三平台要求。需要用范围 ADR 记录“macOS 首发产品 v1.0.0”与“原设计三平台 M3”的关系，原 OB-070/071 等任务继续保留未完成状态。当前仓库的设计版本 1.2 也不是产品发行版本。[R05、R06]

## 三个不同完成线

| 完成线 | 必须交付 | 可用的名称 |
|---|---|---|
| macOS 开发 MVP | 源码安装、真实 CLI/API→Agent→Broker→工具→验证；故障后可安全核对；目标集成可运行 | 开发者内测 / alpha |
| macOS 用户 beta | 图形客户端、上手引导、诊断、干净机器安装、真实集成、候选证据 | macOS beta |
| v1.0.0 正式版 | 范围内能力全验收、签名公证包、兼容契约、迁移恢复、更新策略、文档官网和支持流程 | 已验证平台的稳定版 |

SemVer 1.0.0 要明确公共 API 和兼容规则，不是“所有设想都写完”。CLI JSON、控制 API、事件 DTO、配置结构、错误码与支持范围应明确哪些稳定、哪些实验性。DB schema、协议、运行资产和文档版本独立记录。[W01]

## 首发范围建议

| 必需 | 允许有界实现 | 首发之后 |
|---|---|---|
| 一个 owner/profile/设备；默认单活动任务 | 审批等待与运行队列语义明确 | 多设备、团队、并行多 Agent |
| 云 Provider + 经验证的本地 Provider | 云/本地能力表按具体模型版本填写 | 新 Provider 的广泛兼容 |
| 文件读取、产物、受审批补丁、受限执行 | 只覆盖明确工作区和语言/资产 | 任意宿主 shell 和任意插件市场 |
| Browser 与固定版本 stdio MCP | 先锁定少量可验证工具/受控场景 | 广泛站点自治、自动安装任意 MCP |
| 飞书任务、审批、取消、恢复、回执 | 单专用应用和配对身份；可先普通卡 | 其他 IM 和独立手机 App |
| 中英 Tauri 客户端与只读执行图 | 图展示事实、结果、公开计划摘要 | 隐藏推理展示、会触发动作的历史回放 |
| 停止、恢复、备份、诊断、安装升级 | 可用受验证的手工升级作为明确首发方案 | 无验收支撑的静默自动升级 |

如果决定删减 Browser 写动作、本地 Provider 或飞书等原 MVP 必需项，应把发行范围改成明确的较小版本并记录 ADR；不能把对应必需测试临时改为“不适用”后宣称原 MVP 完成。

## 七条产品场景

1. 从新 profile 打开应用，选择工作区和已验证模型，完成一次文件读取与带来源的总结。
2. 请求修改受控文本文件，展示精确 Diff，批准后写入；批准后文件被用户改动则拒绝覆盖并重新提案。
3. 在受控测试站点完成浏览器读取及范围内写动作；记录最终 origin、页面版本和独立副作用次数。
4. 使用锁定的隔离 MCP 只读工具完成任务；工具表改变、初始化超时或隔离不可用时给出明确失败。
5. 从飞书发任务、确认审批、取消与查看结果；重复事件不创建第二效果，旧卡片不能覆盖新状态。
6. 云调用与真实本地模型分别完成其支持的场景；本地模型不可用时不回退云；OFFLINE 的所有受管出口被验证。
7. 真实 daemon/worker 在已派发但未记录回执的窗口被强杀；重启保持 UNKNOWN/RECONCILING，独立核对后恢复，不盲重放。

## 里程碑与退出条件

| 阶段 | 主要交付 | 退出条件 |
|---|---|---|
| S0：范围与基线 | 固定 SHA、能力清单、命令映射、测试环境、任务纠偏 | 没有互相矛盾的完成声明；知道每项门禁在哪台机器运行 |
| S1：开发 alpha | 第一条真实模型/工具闭环、预算、审批、取消、可信恢复 | 真实进程入口通过；安全反例不产生效果；结果由验证器确定 |
| S2：功能 alpha | 两 Provider、Browser、MCP、飞书、可查询事实事件 | 七场景按声明范围完成；未知结果可解释且可处理 |
| S3：用户 beta | Tauri、配置生效、图/时间线、上手、诊断、可装包 | 新用户无需读工程设计即可启动第一条任务；UI 断开不丢控制面 |
| S4：发布 beta | 签名公证、迁移恢复、更新方案、完整资产清单、真实 Mac 门禁 | 干净机器安装/更新/卸载有证据；篡改制品拒绝；无 S0/S1 缺陷 |
| S5：RC | 候选固定、全量回归、浸泡、真实试用、文档官网一致 | 同候选 SHA 与最终包 hash 的全部必需门禁 PASS |
| S6：v1.0.0 | 受控提升稳定渠道、发行说明、支持与撤回预案 | 下载链接真实有效；校验/签名可核对；发布后 smoke 通过 |

alpha/beta/rc 是本计划阶段标签，最终 Git tag 和 Python 包版本映射需在 V1-030 定义。例如显示标签 `v1.0.0-beta.1` 与 Python 元数据 `1.0.0b1` 分开映射，不能随意混写。

## 日历安排：先估范围，再按证据调整

以一名主开发者使用 AI 辅助、拥有 Mac 和专用集成环境为前提，建议先预留 **8-12 周** 的排程窗口，首周用真实闭环的耗时重估；若需补设备、签名资格或集成缺陷较多，按 **12-16 周** 留余量。该范围是规划假设，不是对现有代码的工时测量或交付保证。

| 时间窗口 | 主路径 | 可并行工作 |
|---|---|---|
| 第 1 周 | S0；真实闭环最小切片；修 Keychain/recovery 关键边界 | README 首屏、About 草案、官网信息结构 |
| 第 2-4 周 | runtime、取消恢复、独立崩溃、MCP/Browser/Provider | 贡献文档、用户指南骨架、Tauri 薄壳 |
| 第 4-6 周 | 飞书与客户端完整交互、配置激活、诊断 | 官网内容、演示脚本、下载数据合同 |
| 第 6-8 周 | 安装包、服务、签名公证、升级恢复、SBOM | 真实截图/视频、网站可访问性与链接测试 |
| 第 9-10 周 | 小范围 beta、性能与浸泡、缺陷逐项闭环 | 修正文案、支持与FAQ |
| 第 11-12 周 | RC 冻结、干净机器彩排、正式发布 | 发布后 smoke 与后续补丁排期 |

依赖满足时可提前推进；核心安全和恢复问题未通过时，不能用文档或官网完成度抵消。首周先做 V1-001/002/003/004/007/008，随后按 V1-010 起的依赖图选择任务。

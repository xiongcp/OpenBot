# 开发执行、逐项提交与首周清单

## 任务组织

新任务 V1-001 至 V1-060 是对原 OB-001 至 OB-096（100% 覆盖全部 96 项原编号）的交付切片和验收补充。实施时请将本执行包放置在 `plan/v1_0_0/`（或仓库外独立目录），切勿覆盖仓库根目录的 `tasks/backlog.json`、`tasks/TASKS.md`、`README.md` 和 `diagrams/`，确保 `validation/verify_design.py` 与 `verify_components.py` 始终通过。前 55 项服务于拟定首发范围，56-60 为后续扩展；其中更新器等可在明确范围决策下采用已验证替代方案。所有 PLANNED 状态均表示本方案尚未执行，不否认对应模块已经存在。

每个任务有原任务映射、负责人方向、依赖、交付物、步骤、验收与负例。S/M/L 表示相对复杂度，不能直接当精确工作日。执行代理先复核当前源码，若任务已完成则补证据并据实关闭，不能为满足清单重写已有代码。

## 分工与并行边界

主集成者负责共享合同、数据库迁移、依赖锁、策略、index/commit/push 和最终合并候选。其他代理可以并行做独立审查、测试设计、文档或在明确文件归属的独立工作树实现。共享 checkout 不同时让多个代理修改同一文件或 index。若当前项目约束要求单工作树，保持该约束，仅并行只读审查。

核心 runtime/API/状态协议是关键路径；UI 可依据固定 DTO 开发；官网可以用明确标记的待发布数据并行完成；真实 screenshot、正式下载和最终支持表等待实际候选。

## 一个问题一个 commit，一次 push

用户已要求每修复一个问题就提交并推送一次。实施时无需每项重复询问此授权；必须先确认实际仓库、分支、push 端点和改动归属。

1. 复现一个独立问题，保存失败证据和预期；不把多项不相关缺陷混到同一修复。
2. 做最小可解释修改，运行相关正反例与必要 lint/types。对于安全/恢复问题，回归要观察实际效果。
3. 查看 diff，只暂存本问题明确文件；若修改了 `uv.lock`、`THIRD_PARTY_NOTICES.md`、`packaging/runtime-assets.json` 等受控文件，同提交更新 `release/checksums.json`；确认没有秘密、原始租户日志、数据库或用户无关修改。
4. 使用项目实际作者/签名配置创建一个原子提交；不添加额外工具归属。记录 commit/tree/parent。
5. 检查实际提交树，必要时用干净 checkout 复验，防止未跟踪文件或 hook 修改影响结果。
6. 普通 fast-forward push 精确修复 SHA 到已确认目标分支；不强推、不附带标签、不自动合并 main。
7. 无论 push 返回成功还是超时，都查询实际目标 ref；只有确认远端已包含本提交才推进下一问题。
8. 查询匹配 SHA 的 CI 与原生门禁（注意修正 `.github/workflows/*.yml` 中仅监听 `mvp/macos-hardening` 的分支过滤），记录 introduced_by_sha 和 verified_on_sha，不能把“已推送”写成“验收通过”。

若 push 失败/未知，先解决这一候选，不累计第二个待推修复。若 push 已确认但 CI 被另一项独立已识别的基线故障阻塞，可保留 CI_BLOCKED 并修下一根因，仍一项一提交；最终必须对累计候选重新验收。

已推送提交不 amend/rebase 改写；后续回归通过新的修复或明确 revert 解决。若远端提前前进，先核对包含关系；只有确定未发布的当前修复才可在新基线上重建并重测。保护用户改动，不 reset --hard、不 clean、不自动 stash。

不要求修复提交包含自己的最终 SHA。commit/push/CI 回执保存在运行账本，避免为每项再补纯记账提交。最终汇总说明哪个提交引入修复、哪个候选完成验证。

## 首周逐日计划

| 日程 | 要做的事 | 当天可审阅结果 |
|---|---|---|
| 第 1 天 | 固定源码/本地改动；核对任务状态与命令；确认首发范围；搭好受控测试 profile | snapshot、能力表、范围 ADR 草案、真实命令表 |
| 第 2 天 | 从真实 `openbot daemon serve` 与 CLI/API 跑最小任务；定位断点；复现 Keychain argv 与恢复信任问题的受控负例 | 第一条失败/成功链路证据；独立修复队列 |
| 第 3 天 | 完成有界 runtime 第一切片；复用现有 BudgetService 与 verify_outcome；测试取消 | 可验证产物、请求计数和取消边界 |
| 第 4 天 | 真实强杀持有 Writer 的进程；独立效果账本；MCP deadline/帧测试 | 崩溃窗口记录；UNKNOWN 不重放证据 |
| 第 5 天 | 对真实链路复盘；更新计划工时；提交 README/能力表的准确草稿；准备客户端 DTO | 可演示 alpha 切片、下一周 ready 队列、风险清单 |

这是建议工作顺序，不是把五天当完整 MVP 承诺。任何 P0 阻断未解决都保留原状态并安排后续；不要为了按日程展示成功而降低验收。

## 发布前必须明确的产品决策

首发平台矩阵、范围删减是否接受、许可证有效决定、模型/外部后端安装方式、自动或手工更新、官网域名和部署目标。这些都可先形成具体草案/差异供审阅，不阻塞独立实现和只读研究；真正改变公开授权、正式发行或部署时按当时已获得的授权执行。

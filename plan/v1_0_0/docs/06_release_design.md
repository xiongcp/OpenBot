# v1.0.0 安装、升级与发布设计

## 先补真正的发行物

当前 `build_pilot_bundle.py` 输出资源阶段和锁 hash；现有 SPDX 文件只列两个聚合包，checksum 列表覆盖五份元数据。这些是发布工程基础，不能代替最终安装包和实际完整资产清单。[R16、R19]

首发建议交付 macOS ARM64 的签名 `.app` 与 `.dmg`；若采用自动更新，还需要所选 Tauri updater 对应的更新包与签名。CLI、Python runtime、daemon/Supervisor、浏览器等已打包依赖或外部前置要求必须清楚标注。用户安装不能意外依赖开发者工作副本、绝对路径或系统中的 uv/Python。

原生最低系统版本不是随意写 `macOS 13+` 或用 CI 名称代替。冻结 SDK、编译 target 和依赖后，在最低声明版本及至少一个当前支持版本验收；没有机器的组合保持未验证。Docker Desktop 等外部后端可作为明示前置条件，但没有它时相关能力必须准确显示不可用。

## 用户级常驻服务

为签名桌面包实现受用户控制的常驻注册/撤销、状态查询、开启登录启动和故障修复。macOS 13 及之后可评估 SMAppService 及包内 helper；必须验证用户批准/拒绝、登录重启、路径移动和卸载的行为。生成 plist 或直接 Popen 不等于完成注册。[R20、W05]

普通任务运行不需要 root。UI 关闭不终止 daemon；显式停止/卸载只回收本项目登记的进程和容器，不能按宽泛进程名杀其他程序。注销后的边界要如实说明，不能承诺用户级服务在登录前处理桌面任务。

## 签名与公证链

对最终包含的可执行内容、helper 和本地库进行与其角色匹配的签名，采用必要的 Hardened Runtime/entitlements；用 Developer ID 分发路线执行公证并保存结果，staple 后再生成最终分发包校验值。签名顺序、嵌套组件和最终包装字节要在流水线固定。[W06]

真正的首开测试从浏览器下载带正常 quarantine 的发布候选开始，不能用移除 quarantine 或关闭 Gatekeeper 的方式通过。签名、公证、Tauri 更新签名、GitHub provenance 各自证明不同内容，任何一项都不替代产品功能/安全验收。[W06-W08]

## 更新状态机

建议顺序：检查候选与兼容性 → 进入持久维护态并禁止新派发 → 核对在途/未知动作 → 停止并确认旧 daemon/worker/容器退出或隔离，封住旧 epoch → 一致性备份 DB 与 artifact manifest → 验证新包 → 原子安装切换 → migration → 启动健康检查 → 解除维护态并恢复接收任务。迁移与健康检查期间继续持有维护锁；即使新服务自启也不能提前接单，不能让新旧 epoch 并发执行。

更新不得强行把 UNKNOWN 标完成以便继续。下载失败、签名失败、空间不足、进程未退出和 migration 失败都需有确定恢复点。不能让旧二进制读取不兼容的新 schema。回退要同时满足 binary/DB/资产兼容；恢复备份也不会撤销已经发生的外部效果。

v1.0.0 可以通过明确范围决策采用经过验收的手工签名升级，暂缓自动下载/安装 UI，但一致备份、迁移、失败恢复与版本兼容不可省略。若启用 Tauri updater，使用受信签名验证，按明确 stable/beta 渠道发布；不要把更新公钥当作 Apple 签名证书。[W07]

## 最终发布清单

| 类别 | 至少包含 |
|---|---|
| 制品 | 最终 DMG/app 更新包、大小、SHA-256、架构、最低系统、下载 URL |
| 运行资产 | 实际 Python/Rust/前端依赖、native 库、浏览器、模型/镜像等打包与外部资产边界 |
| 版本 | 产品、API/协议、配置、DB migration、模型/工具资产、文档 |
| 供应链 | 对实际制品生成 SPDX 或 CycloneDX、许可证/NOTICE、漏洞处置记录、构建来源 |
| 系统证据 | 签名/公证/首开、权限、登录启动、停止/卸载、升级恢复 |
| 产品证据 | 测试候选 SHA、最终制品 hash、真实场景、故障、beta 反馈与未决问题 |
| 公示 | release notes、支持表、已知问题、升级说明、反馈渠道 |

公证/签名可能引入时间相关字节，不能简单用最终 DMG 完全字节相等作为唯一“可复现”定义。分别记录可重建输入、未签名内容对照与最终签名制品 hash；必须说明可复现边界。

## CI 三层设计

PR：合同、类型、关键安全反例、迁移、客户端逻辑、文档链接与示例。Nightly/显式资格：真实 Mac、隔离执行器、专用集成与浸泡。Release：固定候选构建、真实最终包测试、签名/公证、SBOM、来源和发布门禁。

未受信 PR 不获得生产或签名秘密。对 workflows 的名称、事件、实际 checkout SHA 和 run attempt 逐项核对；PR 合并 ref 与修复 head 不混同。若最终 merge/tag 改了被测内容，重新验证新的候选和制品。发布工作流校验必需 job 和证据身份，不能仅看“所有已出现的 job 都绿”。

## RC 与发布当天

1. 冻结范围、已知问题和候选 SHA；只接纳必要阻断修复。
2. 从锁定源码构建，完成最终签名、公证、装订和包装，生成最终字节的校验值、SBOM和来源证据。
3. 对这一确切候选在干净 Mac 保留 quarantine 验证在线/离线首开、安装、首次任务、停止、升级/恢复 smoke；所有证据绑定同一 SHA 和最终包 hash。签名或包装后若字节再变，重新核验受影响门禁。
4. 准备具体 release 草稿、版本标签、下载页面和更新渠道差异供审阅。
5. 正式发布按仓库的实际授权与保护规则执行；本次规划及逐问题 push 授权不自动扩展成发版/部署授权。
6. 发布后从公开链接重新下载核对 hash，运行最小 smoke；官网 stable manifest 与下载链接保持一致。

回退先暂停有问题的更新推广、保留诊断与旧发行物，再发布修复版本或明确恢复指引；不覆盖同一版本的已发布字节。设一名发布负责人和一名复核者，紧急修复仍保持每问题独立提交与候选回归。[W01、W09]

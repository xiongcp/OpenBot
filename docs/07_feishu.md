# 飞书入口与远程交互

v1.2复用官方lark-oapi的通信与事件类型，先交付普通卡片。nanobot/LangBot仅作适配和降级模式参考，复制代码需填写来源台账；其队列、配对和工具执行循环不能替代OpenBot控制面。相关SDK准入和阻塞故障场景见13_component_qualification的Q10。

所核对的SDK源码与历史issue存在发现请求未设timeout的情况，实施时按精确锁定版本确认，优先上游修复，必要时采用有回归测试和退出条件的窄补丁。不要盲目全局monkey-patch requests；不能只在可能阻塞的同一事件循环里运行watchdog。supervisor从进程外执行hard deadline与重建，确认旧Gateway退出再启新实例。[R10]

初始化、导入和握手分别计时；U3引用的24.27秒属于具体issue样本，不是所有平台的门槛。卡片业务审批TTL、回调token和API可更新窗口分别建模，按选定卡片版本和真实租户验证，不将14天/30天等未完成验证的数值写成通用逻辑。[R11]

## 接入约束

飞书是首个正式远程入口。MVP采用企业自建应用的出站长连接；同一app只允许一个活动gateway。官方长连接消息是竞争消费而非广播，多个client不能当作不同电脑的任务路由；每个应用连接数量也有平台上限。[S01]

没有公网IP不等于没有配置成本。安装向导要检查应用类型、tenant、事件订阅、回调版本、机器人权限、测试用户、发消息权限和凭据是否有效。飞书与Lark域名/区域配置分开，禁止未经告知切换区域endpoint。

电脑休眠或关机时无法依靠已经断开的WebSocket继续运行任务。本地常驻服务只能承诺在线时接收、恢复后重连和恢复本地已持久化任务；不能承诺离线期间所有未收到的消息无限补发。需要离线收件箱或远程唤醒时，另设计relay/设备路由与新信任边界。

## 事件与回调分流

| 类型 | 处理路径 | 成功判定 |
|---|---|---|
| im.message.receive_v1 | 校验来源，规范化，向daemon提交inbox事务 | 持久化成功后快速返回SDK要求的响应 |
| card.action.trigger | 校验operator与卡片绑定，提交批准或拒绝事务 | 返回结构化toast/卡片结果，不等待工具执行 |
| 网关状态 | 心跳、断线、鉴权失败、重新连接 | 写入health事件，不生成普通用户Task |
| 飞书附件 | 保存元数据，异步下载到隔离暂存区 | 类型、大小、hash与数据分类通过后可引用 |

官方要求回调在3秒内响应，且同步回调不提供补推；普通事件与卡片回调不能使用同一重试假设。[S01] WebSocket方式通过SDK序列化响应，不在代码里假装它是收到一个公网HTTP请求。HTTP Webhook属于另一个可选transport，要额外实现签名、时间窗口与重放防护。

接入线程不得运行模型、下载文件或等待shell。Gateway只做小对象解析并调用daemon的有限接口。首次SDK初始化与重连分别计时；若SDK包含阻塞网络调用，应在独立进程中隔离，以heartbeat watchdog重建该进程，避免不可取消线程持续堆积。

## 回调时限与数据库背压

设置业务处理总deadline，目标p99小于1秒，并保留平台网络和SDK响应余量。队列未接受、writer过载、数据库不可写或超过开始执行的deadline时，返回“当前无法处理，请稍后重试或本地处理”，不返回“批准成功”。

对已进入提交阶段但响应丢失的情况，数据库记录是真实结果；重复点击读取现有决策。不能因客户端显示超时就再次批准，也不能把一次已持久化批准反悔成“未发生”。任务详情提供查询接口，避免用户只能靠toast判断。

写队列中的callback command要带deadline与request_id。尚未开始且过期的命令必须丢弃；正在事务中的deadline、回滚与提交结果按可观测状态记录。拒绝把超时请求留在后台数分钟后静默执行。

## 卡片状态与更新

卡片展示Task摘要、目标工作区、当前步骤、operation影响范围、审批有效期、执行状态与查看产物入口。按钮value只携带不透明ID和nonce；收件人、工具参数、权限等从服务端不可变记录读取。

每个Task有单调递增card_revision。Outbox为同一卡片串行投递；低revision更新丢弃或合并，不让延迟的“处理中”覆盖已经完成的“成功”。进度更新按时间和内容变化节流，尊重429和Retry-After；优先保留审批与终态通知。

MVP先实现普通消息卡片加OpenAPI更新；CardKit作为可用时的增强能力。无CardKit权限也能完成任务和审批，不能让“流式卡片漂亮”成为运行时可靠性的前提。

## 三种期限互相独立

| 对象 | 含义 | 本地规则 |
|---|---|---|
| approval_expires_at | OpenBot允许开始执行某Operation的期限 | 可配置，默认短期；到期重新生成审批 |
| card callback token | 一次用户交互产生的延时更新凭证 | 从回调实际产生时计时，不从最初发卡计时 |
| message/card生命周期 | 平台对更新或交互的限制 | 由API版本与返回码控制，不覆盖本地授权期限 |

原材料写的token“30分钟、两次”需要在所用接口与SDK版本组合上确认，不能与其他卡片API混用。[S02] 正确测试应先发生callback，再推进时钟超过token TTL，验证使用次数耗尽与过期时走普通OpenAPI或新消息。仅把卡片放45分钟再点，并不能验证本次callback token已经过期。

本地审批已过期时，旧卡片即使还能点击也不能授权；原卡无法更新时，新卡引用同一Task并展示当前真实状态。回调token只用于卡片更新，不能当作执行授权token。

## Outbox投递语义

业务状态与通知意图同事务提交，sender在事务外发送。通知允许至少一次尝试；对平台明确支持的幂等参数保存稳定key并遵循有效期。若远端接受后本地尚未记账，先根据已知message_id或查询能力核对；无法核对则UNKNOWN，不假设发消息天然恰好一次。

向owner发送任务状态属于任务反馈；向第三方发送业务消息必须经过message.send审批，绑定明确账户、收件人ID、内容hash和附件。两个动作都要有receipt，但权限不同。

## 运维与失败体验

连接健康记录last_frame、last_pong、last_successful_send、auth_status、reconnect_attempt与queue_depth，空闲没有业务消息不能直接推断失联。退避有上限与随机抖动；凭据错误进入需要用户处理状态，不无穷重连。休眠后重建连接，检查审批时间、预算和未知动作。

用户可用的命令至少包括“新建任务”“查看状态”“待审批”“取消”“帮助”。同一输入的重发以event_id去重；用户主动复制同样文字发第二次是新的请求，不能仅按文本hash悄悄吞掉。被撤销的owner无法继续批准旧卡片或通过重新配对绕过本地确认。

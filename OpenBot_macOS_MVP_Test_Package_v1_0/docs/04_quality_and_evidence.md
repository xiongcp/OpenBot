# 真实任务质量、失败定位与证据样例

## 固定任务集

使用8类任务，每类至少3个冻结输入，共24个场景。模型、提示、输入文件hash、允许副作用、验收脚本与预算在正式候选测试前固定。测试目标优先采用具有客观产物或状态断言的简单任务，避免只能由另一个模型给主观评分。

| 场景 | 用户动作 | 客观验收 |
|---|---|---|
| 仓库定位与只读分析 | 找到指定函数并给出文件定位 | 路径/符号正确，无工作区写入，无额外网络 |
| 两文件修复 | 修改合成项目的实现与对应测试 | 指定测试通过，非目标文件和用户脏改动保持 |
| 受限测试执行 | 执行合成项目的允许测试命令 | 在已合格后端内执行，出口/CPU/内存/进程约束实际生效 |
| 注入页面提取 | 从包含恶意指令的受控页面提取结构化数据 | 提取正确，页面文本不能赋权，canary无外泄 |
| MCP结果不明 | 工具效果完成后server断连 | effect_count=1，不盲重试，UNKNOWN可核对 |
| 飞书跨重启审批 | 发任务，等待审批时重启，再批准 | 任务与审批身份保持，卡片重放不重复执行 |
| owner撤销 | 撤销owner后点击旧审批或用旧token | 请求被拒绝，外部效果计数不增加 |
| LOCAL_MODEL与OFFLINE | 切换两种模式并故意缺少本地资产 | 路由与出口符合模式，缺资产明确失败，无隐式云回退 |

确定性测试场景要求全部符合预期。真实模型任务完成率、成本、延迟和质量先做一次独立试运行测量，再冻结正式门槛；不能在看到某次失败后降低该次阈值。若尚无产品指标，建议将这24个简单场景作为必须完成的演示集，复杂开放任务另做探索性评估，不用小样本通过率声称长期可靠。

## 必须记录的指标

每个场景记录Task终态、实际产物hash、允许与实际效果、审批数、工具请求数、真实效果数、模型调用次数、provider usage、估算与实际成本区别、完成耗时、失败分类和UNKNOWN核对结果。汇总时分冷启动/热启动、在线/本地、模型版本和缓存条件；不要把不同配置混成一个百分比。

内存与长时运行检查采用固定负载下的多时点测量，观察清空任务与GC后的稳态，不单凭一次RSS升高就认定泄漏。发现趋势后再用具体对象、任务或资源生命周期定位。性能变更必须保留安全与恢复回归，不能靠取消审计、关闭持久化或放宽隔离换取速度。

## 故障定位的分流

| 观察到的失败 | 首先核对 | 常见修复方向 | 必须补的回归 |
|---|---|---|---|
| 任务创建后没有任何动作 | 真实CLI/session、认证API、scheduler是否接通；队列与状态是否持久化 | 修复入口装配、错误传播或队列唤醒 | 新console进程完整路径，重启后任务仍可见 |
| 审批重复导致多次效果 | event/decision幂等、claim条件更新、Operation与Attempt标识、provider key | 将竞争决定纳入事务并保持稳定业务标识 | 20并发决定、重放与重启后效果数 |
| 取消显示成功但仍出现新派发 | 取消提交时点、dispatch复核、已开始效果与新动作的区别 | 修复两次短事务间的条件核对 | 两种事务顺序及取消后已发生效果的诚实报告 |
| kill后重复执行 | 是否已持久DISPATCHING、旧执行域是否实际失效、核对证据 | UNKNOWN隔离与结果查询，禁止非幂等盲重发 | 真实SIGKILL与独立效果账本 |
| SDK超时后费用/请求激增 | SDK内建retry、应用retry、实际网络次数、budget占用 | 唯一重试负责人、deadline与未知成本保留 | 429/5xx/断流/超时对请求计数 |
| 容器/浏览器残留 | CLI PID与真正执行域是否混淆，资源ID是否登记 | 引擎/OS真实查询，按所有权停止与清理 | 取消、崩溃、重启、半完成导出的资源核对 |
| Keychain测试绿但真实调用失败 | 是否用了stub、是否当前登录会话、后端和授权范围 | 使用实际后端与最小canary，拒绝明文fallback | 真实读取/轮换/拒绝/撤销 |
| Browser或MCP有成功报告但无效果 | 是否仅运行fixture、是否真有浏览器/server PID与协议字节 | 补真实transport与OutcomeVerifier | 独立服务端/DOM/效果账本验证 |
| 飞书显示旧状态或重复反馈 | Inbox去重、Outbox revision/429、重连与卡片更新语义 | 稳定事件键、顺序约束与降级反馈 | 乱序/重复/过期token/重启 |
| 备份恢复后产物丢失 | Artifact清单、GC固定、摘要、secret_ref与秘密绑定 | 一致性快照与恢复验证 | 缺产物拒绝、空profile恢复、旧库迁移 |
| 本地绿CI红 | Python/架构/依赖组、pytest入口、路径分隔、工作流是否执行 | 修复一致的工具链与真实收集路径 | 干净环境与同SHA远端CI |

## 有意义的修复证据

最小失败回归必须能在修复前暴露问题，并在修复后通过；必要时在隔离临时worktree对原SHA确认失败，避免污染用户改动。不要为每个简单文案改动补镜像实现的测试。行为、授权、恢复、持久化与平台修复需要验证真正失败路径。

提交前检查的不只是pytest退出码，还包括测试是否收集到预期用例、是否跳过必要路径、断言是否仍然有约束、是否真正使用产品入口。若修改了测试期待值，要说明依据哪个产品合同修正，不能将错误行为重新定义为正确。

## 一份运行记录的最小内容

运行元数据包含run_id、case_id、evidence_kind、source_sha、tracked_tree_sha、lockfile_sha256、环境/架构、命令、开始结束时间、退出码、结果、原因、证据路径/摘要。只有采集过的值可以填写；未知用null或NOT_RUN。源码审查快照SHA与本机运行SHA分别存放。

一份问题记录包含issue_id、severity、失败用例、最小复现、预期/实际、根因、影响范围、修复文件、针对与相关回归、测试tree、introduced_by_sha、远端分支/推送确认、CI run与verified_on_sha、未测范围。提交自身SHA产生后才写入外部运行账本，避免为自引用不断amend。

## 收尾与资源清理

清理只依据本轮资源清单：测试profile、测试Keychain服务名、受控浏览器profile、登记PID/创建身份、容器ID、专用网络与配额卷。先确认对应执行域停止，再导出必要证据和清理；不要删除用户默认profile、系统Keychain、已有工作区或非本轮容器。清理未完成也是验收结果，需要保留BLOCKED或失败记录。
